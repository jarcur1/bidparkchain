# Booking policy proposed for review

This is a proposed policy, not product approval or a description of deployed protections. It accompanies the [pilot policy](pilot-policy.md) and [decision issue #1](https://github.com/jarcur1/bidparkchain/issues/1). The initial pilot is an invite-only Austin, Texas rehearsal using synthetic listings for plausible private spaces: no actual parking, delivery, real bookings, or real funds. A future real-inventory program would be limited to authorized private off-street spaces, subject to separate approval. No on-chain record promises or verifies physical access.

## What the current rehearsal actually does

Auctions created with `createAuction` or `createSpaceAuction` (version 1, what the app creates unless **Protected booking** is ticked) do **not** implement the protected policy below; auctions created with `createProtectedAuction` do, as described in [protocol version 2 in the contract](#protocol-version-2-in-the-contract). An initial illustrative Sepolia rehearsal is allowed only after the infrastructure gates in the pilot policy, and needs a fresh deployment of the current contract. Sepolia means Ethereum Sepolia L1, chain ID 11155111, with faucet-funded native test ETH only. Verify the supported operating window before shared deployment because published lifecycle guidance conflicts; stop if it cannot be confirmed, rather than automatically switching network or using mainnet.

- Bids close at `bidEnd`. Anyone can manually settle at or after that cutoff, including after parking starts or ends; there is no settlement timeout. An optional server-side keeper can settle due auctions automatically; it is off by default (see [hosting](hosting.md#automatic-settlement)). Settlement without bids records no winner or payout. The host can cancel only while there are no bids and the auction is unsettled.
- Only the host can claim a payout, at or after `parkingEnd`, and only for a settled auction with a paid winning bid. The contract does not check physical delivery. Outbid bidders can withdraw their credited principal; the current host payout is a direct transfer on the host's claim, not a protected-protocol pull-credit mechanism.
- For version 1 auctions there is no post-bid booking cancellation, seller-failure refund, dispute hold, no-show or overrun protection. No version has an automatic gas refund. Transaction senders pay their own gas. A settled on-chain winner is not evidence of access or a completed booking.

The keeper from [#22](https://github.com/jarcur1/bidparkchain/issues/22) calls the same permissionless `settle` as the UI. Manual settlement stays available and is still required wherever the keeper is not enabled. For a protected auction it settles only before parking starts. After that it calls the permissionless `expire` on one that was never settled, and `expireDispute` on a report still open at `E + 72 hours`. It never decides a report, never cancels, and never claims a host payout; a report held within its window is left to the resolvers.

## Proposed future protected protocol

The following requirements are for a new, explicitly versioned implementation under [issue #18](https://github.com/jarcur1/bidparkchain/issues/18), not for the current contract. Protected behavior may be rehearsed only after it has been implemented and its applicable gates met; even then, a rehearsal is not authority to accept real bookings or funds. Version migration must preserve the rules under which each auction was created; do not silently apply this matrix to existing escrow.

### Definitions and ordering

`B` = bid end, `S` = parking start, and `E` = parking end, expressed as UTC instants. Display the corresponding local time and time zone for the parking location, including daylight-saving offset. Require `S >= B + 30 minutes` and `E > S`. The reservation interval is `[S, E)` and cannot be extended by this policy. On-chain deadline eligibility is determined by the timestamp of the block including the relevant transaction, not submission time, a UI clock, or a report drafted off-chain. Participants must allow for inclusion delay.

The winning principal is the highest eligible bid locked at `B`; it excludes gas. A win at `B` is only eligibility to settle, not a reservation. A protected reservation exists only after settlement in `[B, S)` and is an on-chain entitlement, not verified delivery. Outbid principal is returned through separately withdrawable pull credits. The transaction sender pays gas; there are no protocol fees or automatic gas refunds under this proposal.

For each winning principal, transitions must be atomic and mutually exclusive: exactly one terminal disposition credits the full principal to the winner or makes the full principal claimable by the host. Credits are withdrawn by the recipient using pull payments; never push value during a state transition. No terminal disposition may be overridden or paid twice. On-chain ordering decides competing transactions within a block, subject to the priority and deadline rules below.

### State and transition matrix

| State and condition | Authorized action / deadline | Next state and principal treatment |
| --- | --- | --- |
| Open auction, `t < B` | Eligible participants bid; host may cancel only before any bid and cannot cancel a paid auction. No winner cancellation is available during the open auction. | Outbid amounts become pull credits. A no-bid host cancellation is terminal with no winning principal. |
| Closed with no bids, `t >= B` | Anyone finalizes the no-bid outcome; no value is required. | Terminal no-bid: no winner, reservation, refund, or host payout. |
| Eligible winner, not settled, `B <= t < S` | Anyone may manually settle. | Settled reservation; winning principal remains held. |
| Eligible winner, not settled, `B <= t < S` | Host may cancel the paid auction by authenticated on-chain action. | Terminal host cancellation: full winning principal becomes a winner pull credit; no reservation exists. |
| Eligible winner, not settled, `t >= S` | Anyone expires the auction; settlement is no longer allowed, including at exactly `S`. | Terminal expired, no reservation; full winning principal is credited to the winner for withdrawal. |
| Settled, early winner cancellation | Only the winner may cancel when `t < S` **and** `t <= S - 24 hours`; the auction must already be settled, so `t >= B`. | Terminal winner refund: full winning principal becomes a pull credit. If settlement occurs too late for this window, this option is unavailable. |
| Settled, later winner cancellation | Only the winner may cancel when `S - 24 hours < t < S`, provided early cancellation did not already resolve the principal. | Record late cancellation; no ordinary winner refund. Principal remains held until the normal host-claim time and remains subject to a timely seller-failure dispute. |
| Settled active reservation, no recorded late cancellation or check-in | Host may record a no-show by authenticated attestation only when `N <= t < E + 24 hours`, where `N = min(S + 30 minutes, E)`. The attestation is not proof of physical arrival or access. | Record no-show only; it has no effect on principal, payout timing, or either party's dispute rights. |
| Settled, host cancellation before `S` | Host may cancel by authenticated on-chain action at `t < S`, unilaterally relinquishing the principal without review. | Terminal host cancellation: full winning principal becomes a winner pull credit. |
| Settled, disputed seller failure before delivery | Winner or host submits an authenticated seller-failure report before `E + 24 hours`, as specified below. The claimed failure must concern the host's withdrawal or inability to deliver before delivery, not merely an alleged overrun. | A timely report holds the principal for review. If upheld, full winning principal is credited to the winner. A timely report prevents payout while pending and, if upheld or unresolved at expiry, takes precedence over a recorded late cancellation or no-show. |
| Timely seller-failure report pending | Authorized operator reviewer decides before `E + 72 hours`, recording an auditable outcome. | Uphold: terminal full winner pull credit. Deny: release the dispute hold; host payout remains unavailable before `E + 24 hours`. |
| Timely seller-failure report unresolved at `t >= E + 72 hours` | Anyone may invoke dispute expiry, including at exactly the boundary. Reviewer decisions are permitted only at `t < E + 72 hours`. | Terminal full winner pull credit; no indefinite lock. |
| Settled, no timely report pending, `t >= E + 24 hours` | Host claims the uncontested principal, including after a denial; no claim is permitted earlier. | Terminal host payout: full principal is credited for host withdrawal. |
| Any terminal disposition | No further settlement, cancellation, report, reviewer decision, refund, or payout may change that disposition. | Only withdrawal of an existing pull credit remains available. |

At `E + 24 hours`, the report window is closed and the host-claim window opens; a report included at that exact instant is late and cannot freeze funds. A denial before that instant does not shorten the hold. A report submitted before the deadline but not included on chain until the deadline is late. A timely report must be registered in the escrow's dispute state before the deadline, so an off-chain message alone cannot race a host claim. If a report is denied while the reporting window remains open, a new authenticated report with additional evidence may be registered before the deadline; it holds funds until resolved or expired. Each report's resolution deadline is the same absolute `E + 72 hours`, not an extension. At or after the host claim or another terminal disposition, reports cannot reopen the outcome.

A timely seller-failure report takes precedence over late cancellation or no-show only when the failure is valid and adjudicated as upheld, or when an unresolved timely claim expires under the specified default. Early winner cancellation, host cancellation and expiry for failure to settle are terminal and cannot later be overridden. The host cancellation paths do not change the winner's cancellation windows or create a new cutoff for the winner. A host cannot gain earlier payout by alleging no-show, and an unadjudicated allegation does not establish physical facts. There is no automatic overrun surcharge and no extension of `[S, E)`; any separate real-world remedy is outside this proposed protocol.

### Reporting, evidence, and bounded review

The winner or host authenticates as the relevant auction account and registers a seller-failure report against the correct protocol version and auction before `E + 24 hours`. On chain, the registration identifies the claimant and includes only an opaque evidence reference; the detailed claim and evidence remain in the restricted operator-managed review channel, not on chain. Both parties can submit relevant evidence to that channel and receive the report status and decision. Access is limited to the authenticated parties and authorized operator reviewers, with appropriate access controls, redacted logs, and an auditable record of submissions, authorization and decisions. Do not put gate codes, private arrival instructions or sensitive evidence in public metadata, calldata or logs.

An authorized operator reviewer may uphold only a valid seller-failure claim and credit the full winning principal to the winner, or deny it and leave the principal for host claim after the normal hold. The reviewer cannot award a partial amount, redirect funds, waive deadlines, override a terminal outcome, or extend the resolution window. A denial must state its reason in the restricted review record. Implement authenticated submission, access controls, bounded reviewer authority, dispute holds and auditability in [#18](https://github.com/jarcur1/bidparkchain/issues/18); they do not exist merely because this document proposes them.

### Protocol version 2 in the contract

`createProtectedAuction(spaceId, metadataHash, minBid, bidEnd, parkingStart, parkingEnd)` creates an auction under this matrix (`spaceId` 0 registers a new space). `bookings(id)` returns whether the auction is protected, its terminal `outcome` (`None`, `WinnerCancelled`, `HostCancelled`, `Expired`, `DisputeUpheld`, `DisputeExpired`, `HostPaid`), the late-cancellation and no-show flags, and the open report's reporter and evidence reference. Existing version 1 auctions are never converted.

| Matrix row | Contract call | Who | When (block time) |
| --- | --- | --- | --- |
| Lead time | `createProtectedAuction` | Space owner or lister | `S >= B + 30 minutes` |
| Settlement | `settle` | Anyone | `B <= t < S` with a winner; a no-bid auction can be finalized at any `t >= B` |
| Expiry | `expire` | Anyone | Unsettled winner, `t >= S` |
| Host cancellation | `hostCancelBooking` | Auction owner or current space owner | `B <= t < S`, settled or not |
| Early / late winner cancellation | `cancelBooking` | Winner | Settled, `t < S`: refunded when `t <= S - 24 hours`, otherwise recorded only |
| No-show | `recordNoShow` | Host | `min(S + 30 minutes, E) <= t < E + 24 hours`, no late cancellation; no effect on funds |
| Seller-failure report | `reportSellerFailure(id, evidenceRef)` | Winner or host | Settled, `t < E + 24 hours`, one open report at a time; again after a denial |
| Review | `resolveDispute(id, uphold, decisionRef)` | A resolver who is neither winner, auction owner nor space owner | `t < E + 72 hours` |
| Report expiry | `expireDispute` | Anyone | Open report, `t >= E + 72 hours` |
| Host payout | `claimPayout` | Auction owner | Settled, `t >= E + 24 hours`, no open report |

Every terminal outcome credits the full principal to exactly one party through `pendingReturns`, withdrawn with `withdrawRefund`; no protected action sends ETH. A winner credit also marks the auction cancelled, which releases its window, so the escrow balance always equals the outstanding credits plus the principal of auctions that are neither cancelled nor paid. Resolvers are added and removed by the deploying account (`setResolver`); that account holds no funds and a resolver cannot decide a report on a booking it is party to. Reports and decisions carry only opaque `bytes32` references.

The contract tests cover ETH conservation through every outcome, role checks, each deadline at its exact boundary, same-block ordering of a report and a host claim, double-resolution rejection, and rejecting or reentrant recipients. The restricted review channel is built: the reporting party posts evidence text or links to `POST /api/auctions/:id/dispute/evidence` and a resolver posts a reason to `.../dispute/decision` (each requires a session and the matching chain state), and the response carries the record's reference, a keccak hash over the whole record, which the on-chain call then uses. Records and a log of submissions and reads are append-only in the database. Only the winner, the host and contract resolvers can read a record (`GET /api/auctions/:id/dispute`); resolvers also get the open-report queue with deadlines (`GET /api/disputes/queue`) in the activity tab. The operator can read the database, so this is access control, not confidentiality from the operator. Check-in is off-chain; see below. None of this has had the independent review required before real funds.

## Arrival instructions and check-in

Private arrival instructions and check-in ([#19](https://github.com/jarcur1/bidparkchain/issues/19)) are stored by the API, never in listing metadata, calldata, events or logs.

- **Who stores them.** The auction's owner, or the space's owner or an approved lister (`isSpaceLister`), signed in with their wallet. Instructions can be set per space (the default for its auctions) or per auction (which overrides the space's). Saving empty text removes them; a change is seen on the next read.
- **Who reads them.** Only the settled winner of that auction, signed in, from 1 hour before parking starts until parking ends (`[S - 1 hour, E)`). Hosts can always read what they stored. The API checks the winner, settlement and booking state against one pinned block (the finalized block on Sepolia, the latest block locally) on every read, so an outbid bidder, any other wallet, an unsettled auction, a cancelled or refunded booking, and a recorded late cancellation are all refused. Responses are `Cache-Control: no-store`.
- **Check-in.** The winner can check in from 15 minutes before parking starts until parking ends. It is recorded once per auction with the time and block number; repeating it returns the first record. The host sees it next to the instructions.
- **What a check-in is not.** It is the winner's own statement that they arrived, recorded off-chain (a verified code adds that a host accepted it). It is not proof of physical access and the contract does not read it: it does not stop a host from calling `recordNoShow`, and it does not open or decide a seller-failure report. If the instructions do not work or the space is unavailable, the winner's remedy is the on-chain `reportSellerFailure` action described above; a host who cannot deliver should use `hostCancelBooking` before parking starts.
- **One-use arrival code.** As an alternative to a plain check-in, the winner can ask for a code (`POST /api/auctions/:id/arrival-token`) under the same rules and the same window as check-in (`[S - 15 minutes, E)`, settled, not cancelled). The code is an HMAC-SHA256 signed payload, using `BIDPARK_ARRIVAL_TOKEN_KEY`, that binds the chain, contract, auction, winner, a random nonce and an expiry of 5 minutes (never past `E`); it can be shown as text or a QR. The host (auction owner, or space owner or lister) submits it to `POST /api/auctions/:id/arrival/verify`. The API checks the signature, the binding, the expiry, and that the booking still holds for that winner at the pinned block, then spends the nonce and records the check-in with the verifying host and time. The same code again is refused with 409, and a code for another auction, a forged or expired code, or a reservation cancelled after issue is refused (400, 410, 403). A new code for an already verified auction returns the existing record with 200. The server stores only spent nonces, not issued codes. Rotating the key invalidates outstanding codes.
- **Not built yet.** Key rotation for the stored text (it is encrypted at rest, see [hosting](hosting.md#arrival-instruction-encryption)), a QR/scan screen in the app (the API returns the code text), and notifying the host of a check-in (see [#21](https://github.com/jarcur1/bidparkchain/issues/21)). The optional settlement keeper from [#22](https://github.com/jarcur1/bidparkchain/issues/22) respects this version's settlement window and expiry, and permissionless manual settlement remains available.

## Calendar export

Any reservation with a lifecycle state can be exported as an `.ics` event from its detail view or its history row; an outbid wallet has no reservation and no event. The status follows the state: leading and awaiting settlement are `TENTATIVE`, upcoming, in progress and completed are `CONFIRMED`, a report in dispute is `TENTATIVE`, and cancelled, refunded and expired are `CANCELLED`.

Times are written as UTC instants rather than as a zone-qualified local time. That is exact across daylight-saving changes in every calendar app and needs no embedded VTIMEZONE; the space's IANA zone and its local wall-clock window (both dates for an overnight window) are named in the description, and a space with no zone says its times are UTC. The UID is `<chainId>-<contract>-<auctionId>@bidpark` in every state, and `SEQUENCE` is the canonical chain snapshot block number (`chain.blockNumber`) the detail or history view was read at, not the lifecycle rank and not wall-clock time. Block numbers only grow, so importing a later export updates the same event whatever state it moved to; until a snapshot has been read, the export is withheld. Private arrival instructions are never included.
